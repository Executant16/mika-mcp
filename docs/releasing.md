# 自动发布 Windows 安装包

普通分支推送只运行 verify 检查。推送 `v主版本.次版本.补丁版本` 标签会运行 release：验证版本号、完整测试、样式与 Schema 契约，准备内置 Python，构建 Windows x64 NSIS 安装包，校验附件，然后正式发布 GitHub Release。任何前置步骤失败都会阻止发布。

流程使用 GitHub 自动提供的 `GITHUB_TOKEN`，无需配置个人 Token。发布完成后会标记为最新版本，并自动生成发行说明；可在发行页编辑说明。

## 本次发布准备：0.1.5（尚未发布）

源码已同步为 0.1.5，不需要重复执行版本更新命令。先修复并通过发布门禁、排除测试产物、核对提交范围，再经授权提交并推送普通分支。推送版本标签会自动正式发布，不用于试跑 CI；安装／升级与原生交互验收完成并取得单独发布授权后，才创建和推送标签。

先完成代码修改，在项目目录用 PowerShell 执行：

```powershell
npm version 0.1.5 --no-git-tag-version
```

这个命令同步 package.json 与 package-lock.json，但不会提交或创建标签。同步 README、相关文档及写死版本号的测试；管理界面当前从应用状态获取版本号，无需修改展示代码。桌面版本更新不要求同时提高 MCP Runtime 版本。

检查并提交本次要发布的文件，推送 main。确认这些操作完成后，再创建并推送标签（每条命令成功后再执行下一条）：

```powershell
git tag -a v0.1.5 -m "Mika MCP v0.1.5"
git push origin v0.1.5
```

标签必须指向包含 release.yml 和全部版本更新的提交。进入 GitHub 的 Actions 页面查看 release 进度；成功后 Releases 中会出现正式版本，包含：

- mika-mcp-setup-0.1.5.exe
- mika-mcp-setup-0.1.5.exe.blockmap
- latest.yml

普通用户下载安装包；另外两个附件供自动更新使用。安装包沿用当前未签名配置。

## 失败处理

构建或测试失败时，查看 Actions 中失败步骤的日志。发布步骤之前的临时下载故障可以重新运行失败的工作流；上传或发布步骤失败时，先确认 Releases 中是否已经留下草稿，再决定处理方式。需要修改代码时应修复后使用新的版本号和标签，不移动已经发布的标签。

流程不会覆盖同名已有 Release，重复发布同一版本会失败。若上传中断留下了草稿，先核对其附件与日志，再处理该草稿；不要另建同版本发行版，也不要直接发布缺附件的草稿。
