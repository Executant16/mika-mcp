>
> 它约束 `renderer/` 下所有样式改动。任何新增或修改的 CSS，必须符合本文。

> - `npm run lint:css` —— 只**报告**当前全部违规，**不**作为门禁

## 一、唯一事实来源

所有颜色、字号、圆角、间距**只能**来自 `design-tokens.css`。

业务 CSS 中**禁止**出现：
- 任何字面量颜色（`#fff`、`rgb()`、`rgba()`、`hsl()`）
- 任何字面量 `font-size`
- 任何字面量 `border-radius`
- 任何 `!important`

需要新颜色时，**先在 `design-tokens.css` 里加一个语义令牌**，再引用它。
不要因为"只用一个地方"就直接写死。

### 令牌的路径唯一性

**`styles.css` 不得定义任何 `--token`。** 业务 CSS 只消费令牌，不生产令牌。

历史：`styles.css` 曾有一份 `:root` 令牌块，与 `design-tokens.css`
重复定义了 **19 个**令牌。由于 `styles.css` 加载在后、选择器权重相同，
它**一直是"赢"的一方**——`design-tokens.css` 里的同名值全是死代码
（例如 `--bg` 实际生效的是 `#141414` 而非文件里写的 `#080b11`）。
后果是"改令牌"这个动作不可靠：改了令牌文件看不到效果。

这与覆盖层是**同一个问题的两种形态**：只要有两条路径能定义同一个值，
后加载的那条就会悄悄接管。

**一条可执行的判据**：`styles.css` 中出现行首 `--xxx:` 即为违规。
本仓库已有测试断言这一点（`chat-ui-compact.test.js`）。

### 令牌替换必须是"保值"的

把字面量换成 `var(--token)` 时，**如果两者值不相等，就不是重构而是改设计**，
必须单独走设计评审。判据很直接：

> 把所有令牌引用展开回实际值后，替换前后的文件应**逐字节一致**。

这条判据能机械执行，因此**不要靠肉眼比对**。第 16 轮的替换脚本先跑这条校验，
通过了才写盘（脚本一度因为把"原文里原本就存在的 `var(--radius-sm)`"也当成
新引入的而误报不等价——校验本身也要写对：**两边都要展开**）。

**为什么这条重要**：本机 Electron GUI 已无法启动，视觉回归跑不了。
在这种条件下，**"保值"是唯一能保证不出意外的性质**——因为它使渲染结果
逐像素不变，从而完全不需要视觉验证。若做的是近似替换（如把 `13px` 提到
`14px` 以合并档位），就失去了这个保证，必须等 GUI 可用后再动手。

**替换范围受加载链约束**：`browser.html` 只加载 `browser.css`，
**不加载 `design-tokens.css`**。对 `browser.css` 写入 `var(--token)` 会因
变量未定义而使整个声明失效（不是回退，是丢失）。因此本轮只处理 `styles.css`；
`browser.css` 的 29 处尺度字面量属结构性遗留，见 §五 遗留清单。

## 二、表面阶梯

界面由四个层级的表面构成。**相邻层级的 RGB 距离应不小于 25**（满分 765），
否则层级不可见，界面会"糊成一片"。

| 层级 | 用途 | 令牌 | 深色 | 浅色 |
| --- | --- | --- | --- | --- |
| Canvas | 页面底 / 内容区 | `--bg` | `#141414` | `#eef1f6` |
| Structural | 侧栏 / 固定区域 | `--sidebar` | `#171717` | `#f7f9fc` |
| Container | 卡片 / 面板 / 字段 | `--surface` | `#242424` | `#ffffff` |
| Recessed | 卡片内的次级区域 | `--surface-2` | `#2e2e2e` | `#f4f6fa` |
| Recessed+ | 更深的凹槽 / 进度槽 | `--surface-3` | `#3a3a3a` | `#e9edf4` |

**规则**：卡片必须是 `--surface`，且它的父容器必须是 `--bg`。
若两者取同色，卡片就失去了存在感。

> 历史教训：此前浅色主题下 `.app-shell` 与 `.panel` 都是 `#ffffff`，层级色差为 **0**，
> 卡片完全靠一根 0.5px 边框定义 —— 这是界面"廉价感"的主因。

**关于"层级色差"的实际状态（第 15 轮实测，勿被旧说法误导）**：
本文档早期曾写"相邻层级 RGB 距离须 ≥25"。按 `--bg → --sidebar → --surface
→ --surface-2 → --surface-3` 顺序实算，该门槛**从未被满足，也未被满足过**：

| 层级间距 | 深色 | 浅色 |
| --- | --- | --- |
| `--bg` → `--sidebar` | 5.2 | 13.4 |
| `--sidebar` → `--surface` | 17.3 | 15.1 |
| `--surface` → `--surface-2` | 15.6 | 12.8 |
| `--surface-2` → `--surface-3` | 20.8 | 18.4 |

真正在起作用的是**明度阶梯**（深色逐级变亮、浅色逐级变暗，
且 `--surface` 与父容器 `--bg` 的差别足够可见），而非某个统一的欧氏距离阈值。
`--bg` 与 `--sidebar` 只差 5.2 是**有意为之**：侧栏是一块贴合窗口边缘的
结构面，不是卡片，过大的色差会让它显得像浮起来的独立面板。
因此**不要把"≥25"当作验收判据**——它是早期设计意图的残留描述，与现状不符。

## 三、字号阶梯

**只有 6 档，不得新增。**

| 令牌 | 值 | 用途 |
| --- | --- | --- |
| `--fs-xs` | 12px | 最小辅助文字（徽章、脚注） |
| `--fs-sm` | 13px | 次要说明、表格单元格 |
| `--fs-base` | 14px | **正文默认** |
| `--fs-md` | 16px | 强调文本、卡片标题 |
| `--fs-lg` | 20px | 区块标题、图标字形 |
| `--fs-xl` | 24px | 页面主标题 |

**正文不得低于 12px。** 桌面端 1360px 宽下使用 9–10px 正文，等于把信息藏起来。

> 历史教训：此前有 19 种字号，73.5% 的声明 ≤11px，正文主力是 9px 和 10px。

**低于 12px 的字号只有三档，且都必须走令牌。**

| 令牌 | 值 | 用途 |
| --- | --- | --- |
| `--fs-pre` | 10px | 预格式化输出（机器产生、按列对齐的内容） |
| `--fs-11` | 11px | 次要元信息：路径 / 分类标签 / 计数 |
| `--fs-11-5` | 11.5px | 最小徽章与原文块 |

① **预格式化输出区可用 10px。** 只用于"机器输出"而非"给人读的正文"：
`.build-console` / `.task-command` / `.instruction-details pre` /
`.task-worktree-diff pre` 这 4 处。它们是等宽日志与命令回显，长行需要在
一屏内多显示几列；改成 12px 会让日志更早折行、反而更难读。
（`.log-output` 已于第 29 轮移出这一档：日志是给人顺着读的时间线，
每行一句自然语言，10px 中文太小，改用 `--fs-base`。）

② **`--fs-11` / `--fs-11-5` 是历史值的显影，不是新增档位。** 第 40 轮把
styles.css 里 222 处字号字面量收敛到令牌层时，这 15 处原本就是 11px /
11.5px，只是从前藏在护栏之外看不见。收敛的硬约束是"用户看到的字号一个都
不能变"，因此按原值原样发令牌，不就近取整。把它们抬到 12px 会**改变渲染**，
属界面决策 —— 需要在真机上对比密集元信息（路径、徽章）的可读性后再定，
不能由"文档里写着唯一例外"这种措辞倒推。

③ 第 41 轮把这条事实**写进测试**：`chat-ui-compact.test.js` 里那条
"低于 12px 的字号令牌"断言原先用 `--fs-[a-z]+` 匹配令牌名，而 `--fs-11`
这类数值名含数字，正好被正则漏掉 —— 于是"只有一档"这句话在文档里是错的、
在测试里是绿的。现在正则改为 `--fs-[a-z0-9-]+` 并显式列出三档，
任何新增的低于 12px 的令牌都会被拦下。

4 处统一写成 `font: var(--fs-pre)/1.6 Consolas,monospace`。

> **为什么必须是令牌，而不是继续写 `font: 10px/...`**
> 第 27 轮实测证实：护栏的 `declaration-property-value-allowed-list` 只检查
> `font-size` **属性**，而 `font` **简写**里的字号完全绕过检查 ——
> 上列 5 处曾长期（含一处 9px 的无意偏差）未被告警，正是因为这个盲区。
> 既然走令牌，字号就"抬"到令牌层一处集中声明，自带论证与归属；
> 同时让"本项目只有一档低于 12px 的字号"成为**可查询的事实** ——
> 想知道有没有人偷偷用 9px，看 `design-tokens.css` 就够了。
> 例外不再散落在 5 个使用点，也不需要任何 `stylelint-disable` 注释。

> **旧的"护栏盲区补不了"判断已被推翻（第 27 轮）**
> 原话是"给简写加检查需要解析 `font` 复合语法，成本高、易误报，暂不做"。
> 实测证明不需要解析：一条正则就够了 ——
> `/^\s*(?:[a-z0-9]+\s+)*\d+(?:\.\d+)?px/`，挂在
> `declaration-property-value-disallowed-list` 的 `font` 上（见 `stylelint.config.mjs` 3b 节）。
> 实测命中 `8px/1.5`、`700 8px/1.5`、`italic 10px/1.6`、`10.5px/1.6` 四种形态，
> 并放行 `var(--fs-pre)/1.6` 与 `inherit` —— 零误报。
> 教训：**"某条护栏做不了"的判断同样需要实测**，否则它就会变成一块
> 长期不设防的区域；而一个不设防的区域很容易继续长出新的违规。

**字重**只用两档：`400`（正文）、`500`（强调）。
禁止 `600` / `650` / `700` / `750` / `800` / `900`。
中文在这个字重区间会显得又粗又笨，且会掩盖由字号建立的真实层级。

> 历史教训：此前有 31 处用了 650–900 的超重字重，而 500 只有 2 处 ——
> 几乎所有"想突出"的地方都被拉到了极粗。这是界面显得"土"的重要原因之一。

## 四、间距与圆角

**间距**使用 4px 基准网格，只允许：`4 / 8 / 12 / 16 / 24 / 32`
（令牌 `--sp-1` ~ `--sp-6`）。

**圆角**只允许 5 档：

| 令牌 | 值 | 用途 |
| --- | --- | --- |
| `--radius-sm` | 4px | 徽章、小标记 |
| `--radius-md` | 6px | 按钮、输入框、列表项 |
| `--radius-lg` | 8px | 卡片、面板 |
| `--radius-xl` | 12px | 窗口级容器 |
| `--radius-pill` | 999px | 胶囊标签 |

**视觉风格：紧凑专业。** 小圆角 + 1px 锐利边框 + 紧凑行高，
目标是"专业工具"而非"消费级 App"。具体含义：

- 圆角保持克制，最大不超过 12px（窗口容器）
- 边框用 1px 实线且不透明度足够（浅色 `rgba(20,25,35,.17)` / 深色 `rgba(255,255,255,.15)`），
  让分组边界清晰可辨 —— **优先用边框而非阴影表达结构**
- 阴影几乎不用：`--shadow` 仅为 `0 1px 2px`，卡片默认 `box-shadow: none`
- 行高与内边距偏紧，一屏容纳更多信息（这是工具型界面的首要诉求）

> 历史：曾用 `--shadow: 0 22px 60px` 的大投影与 18px 圆角，属于消费级 App 的观感；
> 与"本地开发工具控制台"的定位不符，已改为紧凑风格。

**禁止** `10px` / `11px` / `14px` / `16px` 这类中间值 —— 它们与相邻档位视觉上无法区分。

## 五、图标

统一使用**内联 SVG 线性图标集**，定义在 `index.html` 中，样式由 `styles.css` 控制。

**规格（不可偏离）**

| 项 | 值 |
| --- | --- |
| viewBox | `0 0 24 24` |
| 描边 | `stroke-width: 2`（缩放显示为 18px 时等效约 1.5px） |
| 端点 / 连接 | `stroke-linecap: round`、`stroke-linejoin: round` |
| 填充 | `fill: none` |
| 颜色 | `stroke: currentColor`（跟随文字色） |
| 显示尺寸 | 侧栏 18px / 操作按钮 17px / 列表箭头 16px / 装饰与节点 28px |

**底色规则**

图标容器**可以带同色系淡底**（如 `rgba(108,140,255,.11)`），也可以**完全不带底色**，
但两者不可混用于同一视图。判断依据是**该容器是否需要成组出现**：

- **带底**：图标与文字并排、需要一块视觉承托时（`.action-icon` 31×31、`.step-number` 34×34）
- **不带底**：图标单独居中、下方有文字说明时（总览页三个连接节点）——
  此时底色会与图标争夺注意力，去掉后图标本身更突出

不带底色时**不要保留固定尺寸的容器**（如 `width: 42px; height: 42px`）：
那是为色块设定的尺寸，去底后只会产生多余留白。直接让容器包裹图标即可。

**禁止**

1. **用文字首字充当图标。** 例如用 `N` / `工` / `连` / `W` 代表
   「便携运行时」「本地工具服务」「连接通道」「当前工作目录」——
   这类字母不传递任何信息，只是占位符。状态由**文字标签 + 状态点**表达即可。
2. **混用不同来源的 Unicode 符号。** 此前侧栏混用了
   `⌂ ◇ ▱ ✓ ▣ ✚ ? ≡ ⚙`，分别来自几何图形、标点、杂项符号等不同区块，
   笔画粗细与视觉重量互不匹配。这正是界面"AI 感"的最大来源。
3. **用 `font-weight` 撑图标字形。** 此前 `.nav-icon` 用 `font-weight:700`、
   `.action-icon` 用 `font-weight:800` 来加粗符号 —— 这本身就说明它们不是为图标设计的。
4. **使用 emoji**（跨平台渲染不一致，且无法跟随 `currentColor`）。

### 品牌标记

全项目只有一个品牌符号：**终端提示符 `›_`**（白色尖角 + 强调蓝下划线）。
它在三个地方出现，必须保持同一造型：

| 位置 | 文件 | 尺寸 |
| --- | --- | --- |
| 应用图标（任务栏 / 安装包 / 桌面快捷方式） | `electron/app-icon.png` `.ico`，由 `scripts/generate-icon.js` 生成 | 512 画布，圆角底板 |
| 侧栏品牌标记 | `index.html` 的 `.brand-mark` | 22px（`.large` 为 26px） |
| 启动画面 | `index.html` 的 `.boot-logo` | 34px |

**底板**：`#191c22` 圆角方块。**标记**：白色尖角 + `#6c8cff` 下划线。

**禁止**：紫蓝渐变底板、发光投影、多层描边等装饰手法。
此前三个位置各自用了不同的渐变 logo（`linear-gradient(135deg,#796dff,…)`、
`linear-gradient(145deg,#7c90ff,…)`），彼此不一致且都违反本契约。

> 历史教训：应用图标曾堆叠四个元素（机器人脸 + 霓虹轨道环 + 节点图 + 地球网格），
> 缩到 16×16 会糊成一团。改为单一符号后，图标文件体积下降约 78%
> （ICO 33KB → 7KB，PNG 37KB → 8KB）。

**注意**：启动画面当前被两层机制主动隐藏，都不再依赖 `!important`：
`.boot-screen{display:none; opacity:0; visibility:hidden}`（`styles.css:332`），
仅在 `.booting` 类存在时可见（`:339`）。
历史：该隐藏规则曾是 `settings-compact.css` 里的 `.boot-screen{display:none!important}`，
随该文件拆解并入 `styles.css` 并去掉了 `!important`——因为 `.boot-screen` 没有
与之竞争的同权重 `display` 规则，`!important` 属冗余。
若要恢复启动画面，需移除 `display:none` 与 `opacity/visibility` 两条隐藏意图。

## 六、明确禁止

以下做法在本项目中**禁止**：

1. **装饰性发光、多色渐变、霓虹效果**
   —— 包括 `.hero-card` 那类 `radial-gradient` 装饰光晕。
   渐变仅允许用于表达**连续物理量**（如进度条填充）。
2. **过大的空白卡片**
   —— 卡片高度必须由内容决定。若一个卡片 200px 高却只放两行字，就是错的。
3. **给每个分组都加边框**
   —— 优先用间距和表面色差分隔，边框只在必要时使用。
4. **一个视图使用多个强调色**
   —— 选中态、焦点、链接、主操作统一使用同一个强调色。
   **具体反例**：总览页三个连接节点曾各用一色（蓝 / 紫 / 青），
   连接线又叠了 `linear-gradient(90deg, blue, violet)` 渐变与 `box-shadow` 发光。
   这类"每项一个颜色"的分色方案是"AI 感"的主要来源之一。
   图标容器**统一用 `--blue` + 同色系淡底**（如 `rgba(108,140,255,.11)`），
   与 `.action-icon` / `.folder-illustration` / `.step-number` 保持一致。
   分隔线用 `--border-strong`，不使用彩色渐变。
5. **用 `!important` 覆盖样式**
   —— 需要覆盖时，改令牌或调整选择器权重。
   **唯一的例外**：`[hidden]{display:none!important}`。
   它是平台级隐藏机制，而 `.soft-badge` / `.task-empty` / `.task-dashboard`
   都声明了 `display`（`inline-flex` / `grid`），权重同为 `0,1,0`，
   会凭来源顺序压过浏览器默认的 `[hidden]`。
   不用 `!important` 就只能靠"把该行排到文件最末"来赌顺序——
   任何后续新增的 `display` 规则都会静默破坏隐藏行为，
   这正是 132 个 `!important` 得以蔓延的同一种脆弱。
   该例外已在源码处用 `stylelint-disable-next-line` 逐行放行，
   因此护栏的 `declaration-no-important` 计数仍为 **0**。
6. **靠堆叠选择器权重解决问题**
   —— 选择器权重上限 `0,3,0`。
7. **语义色对比度不达标**
   —— 强调色（`--blue` / `--green` / `--yellow` / `--red` 等）在深色主题下由
   `:root` 定义，**浅色主题必须各自重新定义一组**。
   "浅色主题不定义语义色"是一条最隐蔽的违规：它不报错、不崩溃、不触发任何
   护栏，只是让全部语义色继续沿用"为深色底挑选的高明度值"，落到浅色底上
   集体失效。修订前的实测最低值：

   | 令牌 | 浅色实测最低 | 令牌 | 浅色实测最低 |
   | --- | --- | --- | --- |
   | `--yellow` | 1.45:1 | `--green` | 1.63:1 |
   | `--cyan` | 1.48:1 | `--red` | 2.34:1 |
   | `--blue` | 2.62:1 | `--violet` | 2.65:1 |

   **标准（按实际渲染背景量，不是按纯表面）**：

   | 用途 | 最低 | 依据 |
   | --- | --- | --- |
   | 文字（正文 / 标签 / 链接 / 状态词） | 4.5:1 | WCAG AA 正文 |
   | 图形（图标 / 指示点 / 描边 / 进度条 / 按钮填充） | 3:1 | WCAG AA 非文本对比 |

   **关键：底色 ≠ 纯表面。** 消费点里有大量"同色半透明底"
   （`.action-icon` 的 `rgba(108,140,255,.1)`、`.health-item>i` 的
   `rgba(66,211,146,.1)` …）与渐变端点，必须先用 alpha 合成出**真实底色**
   再算比例，否则会高估对比度。最典型的坑是 `.build-summary.failed`：
   红字压在 `rgba(255,107,121,.08)` 的**自染底**上，红底把对比度吃掉了
   一大截（4.51:1，而同样红字压纯 `--surface-2` 是 5.05:1）。

   **改法**：只调明度，不换色相。因为那些半透明底用的是硬编码的旧色相
   字面量，保持色相就能让它们继续成立，改动面收敛在 `design-tokens.css` 内。

   **怎么验证**：`npm run check:contrast`（源码 `scripts/check-contrast.js`）。
   它从 `design-tokens.css` **真实解析**令牌值（不写死颜色），对 94 个消费
   场景（47 × 2 主题）按"实际渲染背景"复算，有违规则退出码 1，CI 每轮执行。
   **改任何强调色令牌值之后都必须跑它** —— 这是本条规则唯一的执行手段，
   少了它就又退回到"靠人记得"。

   工具本身也有两个防退化设计：
   - `KNOWN_EXCEPTIONS` 里的例外**必须真的命中**，否则脚本报"该例外已过期，
     应当删除"。防止例外清单变成永久豁免的垃圾桶。
   - 输出会打印"最紧场景"及其余量倍数。余量逼近 1.0 时应重新审视该消费点，
     而不是等它跌破。
8. **为不存在的元素写样式（死选择器）**
   —— 删掉 HTML 元素时，必须同时删掉它的样式规则。
   第 18 轮清掉了三个，成因各不相同但都属这一类：

   | 死选择器 | 为什么永远不匹配 |
   | --- | --- |
   | `.ghost-button` | 曾用于"次要操作"按钮，后来全部改用 `.secondary-button`，**HTML 里已无此 class** |
   | `.settings-list` | 设置页重构后不再有列表容器 |
   | `.brand-mark span:nth-child(2/3)` | 品牌标记从"尖角 + 圆点"图形改成 `<svg>` 后，`.brand-mark` 内**已无任何 `<span>`** |

   危害不是"占几行"，而是**误导**：读代码的人会以为存在 `ghost-button`
   这类按钮，于是照着它写（`.brand-mark span` 那两条还带着 `transform: rotate(35deg)`
   这类具体意图，更像真的）。死样式是"文档在说谎"的一种形式。
   **判据**：新增样式前先确认选择器有对应元素；删除元素后全局搜一次 class 名。
   注意要搜 HTML **和** JS 里的动态拼接（`className=` / `classList.add`），
   只在 HTML 里搜会漏。
9. **同一个动作有两个名字（术语不统一）**
   —— 界面文案属于设计系统的一部分，与颜色、字号同等对待。
   第 18 轮统一前，同一个"启动服务"动作被称为「一键启动」，
   同一个页面同时被叫「运行与连接」（导航项）和「一键部署」（正文引用）。
   后者是最明确的违规：**引用同一个页面却给了两个名字**。

   **术语表**（唯一说法，不得另造）：

   | 动作 | 唯一说法 | 实际行为 | 出现位置 |
   | --- | --- | --- | --- |
   | 单纯启动 | **启动服务** | `runRuntime('start')`，**不保存**配置 | 顶栏按钮（未就绪时） |
   | 单纯重启 | **重新部署** | `runRuntime('restart')` | 顶栏按钮（已就绪时） |
   | 保存配置并启动/重启 | **开始部署** | `deployNow()`：保存 + `api.start()` | 一对一引导入口、部署页主按钮 |
   | 体检后的自愈 | **自动修复** | `repairHealth` | 诊断与修复页 |

   **为什么「一键启动」被删掉**：字面上"一键"强调省事，而真正的信息是
   **它不保存配置**。顶栏按钮未就绪时只调 `api.start()`，
   缺配置会失败并把用户导去部署页；hero 的「开始部署」则是先保存再启动。
   两者行为不同，用「一键启动 / 开始部署」两个名字会让人以为它们等价。
   改成「启动服务 / 开始部署」后，**名称直接对应行为**。

   **判据**：同一个动作在全界面只能有一个名字；引用同一个页面也只能有一个名字。
   新增按钮时先查上表，不要新造说法。

### 六.10 同一个页面有三个名字（第 21 轮已删）

**现象**：每个页面标题上方原有一行蓝色小字（`.eyebrow` / `.section-kicker`），
于是同一个页面出现了**三个不同的说法**：

| 页面 | 侧栏（用户点的地方） | 蓝色小字 | 页面标题 |
| --- | --- | --- | --- |
| overview | 总览 | 主页 | 运行总览 |
| deploy | 运行与连接 | **连接配置** | 运行与连接 |
| workspace | 工作区与权限 | **访问与权限** | 工作区与权限 |
| task | 任务状态 | **任务中心** | 任务执行状态 |
| build | 构建验证 | **自动验证** | 构建与验证 |
| health | 诊断与修复 | **系统诊断** | 诊断与修复 |
| guide | 接入指南 | **接入帮助** | 接入指南 |
| logs | 运行日志 | **诊断记录** | 运行日志 |
| settings | 偏好设置 | 偏好设置 | 偏好设置 |

**9 个页面里 8 个出现第三个名字**，第 9 个（settings）小字与标题**完全相同**。

**为什么必须删**（三条独立理由，任一条都足够）：

1. **不提供新信息**——用户已经看到侧栏和标题两个名字，第三个只是同义词，
   迫使他在三个说法间做心理映射。
2. **纯重复**——settings 页小字与标题一字不差，删掉零损失。
3. **抢注意力**——它是页面上**唯一的彩色文字**（`var(--blue)`），
   却压在标题**上方**。视觉动线上先是彩色小字、再是标题，
   而它承载的信息量最低。

**为什么当初没发现**：原作者把它的字号设为 `9px`、字重 `800`，
小到几乎糊成一团，看起来只是个装饰性标记，没人会去读它。
第 14 轮统一字号时按"最小档 = `--fs-xs`(12px)"把它放大到 12px、字重降到 500，
**它才变成一段真正会被读到的文字**，语义问题随之暴露。

> **教训**：字号统一会把"装饰性噪音"升级成"可读内容"，
> 从而暴露原本被尺寸掩盖的语义缺陷。统一字号后要重新审视
> 那些"以前看不清所以没人在意"的元素。

**判据**：同一个页面在全界面只能有两个名字——**侧栏标签**（用户点的地方）
与**页面标题**（用户到的地方）。两者含义重叠时以侧栏为准，
标题可以更具体（如侧栏「任务状态」→ 标题「任务执行状态」），
但**不得引入第三个说法**。

**删除时的连带改动**（漏任何一项都会出错）：

| 文件 | 改动 | 漏掉的后果 |
| --- | --- | --- |
| `index.html` | 删 14 处 `<p class="eyebrow">` / `<span class="section-kicker">` | — |
| `app.js` | `pageMeta` 从三元组收缩为二元组，解构改为 `const [, title, subtitle]` | **`navigate()` 崩溃**：`$()` 是裸 `querySelector`，对 `null` 取 `.textContent` 抛 `TypeError`，页面切换全废 |
| `styles.css` | 删 `.eyebrow, .section-kicker{...}` | 死 CSS（棘轮会记一条） |
| `styles.css` | 删 `.settings-page-heading h2{...}` | 该规则**原本就是死 CSS**（settings 页从来没有 h2），顺手清掉 |
| `tests/` | 补 1 条守护测试 | 回归无人拦 |
| `scripts/check-contrast.js` | 删 1 条 `.eyebrow blue @ surface` 场景 | **不会报错，但会误导**：场景名匹配不到任何节点，让人误以为"还有一处蓝色小字"，实际只是 `.node span` 的重复项 |

**顺带清掉的死 CSS**：`.settings-page-heading h2` —— 原文的 settings 页
也没有 `h2`，这条规则从写下那天起就没生效过。

### 已解决：`--blue-2` 的职责冲突（第 21 轮记录，第 27 轮修掉）

**问题**：`--blue-2` 曾被赋予**两个互斥的要求**：

- 作白字按钮的填充（`.step-pill span`、`.input-action button`）→ 需够**暗**，
  白字才达 4.5:1
- 作进度条渐变起点（`.progress-track` 的
  `linear-gradient(90deg,var(--blue-2),var(--violet),var(--cyan))`）
  → 需够**亮**，压在 `--surface-3` 轨道上才达 3:1

**当时的判断**是"同一令牌不可能同时更暗又更亮，必须拆成两个令牌"。

**实际的解法更简单**：不需要拆新令牌，只需要让两个需求**各归其位** ——
渐变位本来就有现成的合适令牌 `--blue`：

| 用途 | 令牌 | 深色 | 浅色 | 结论 |
| --- | --- | --- | --- | --- |
| 渐变起点（对 `surface-3` 轨道，需 ≥3:1） | `--blue` | `#7391ff` **3.91** ✓ | `#2b59ff` **4.50** ✓ | 改用它 |
| 白字填充（白字需 ≥4.5:1） | `--blue-2` | `#4267ee` **4.77** ✓ | 同值 **4.77** ✓ | 保持不变 |
| ~~渐变起点（原）~~ | ~~`--blue-2`~~ | ~~**2.39 ✗**~~ | ~~4.06 ✓~~ | 缺陷只在深色 |

改动只有一处：`.progress-track i` 的渐变起点 `var(--blue-2)` → `var(--blue)`。

**附带修好了一处不一致**：`--blue-2` 在浅色主题**刻意不重定义**（直接继承深色值），
所以改之前渐变三段里只有起点不跟随主题；改后 `--blue`/`--violet`/`--cyan`
全部按主题给值，渐变配色在两个主题下都自洽。

**验收**：`check-contrast.js` 的 `KNOWN_EXCEPTIONS` 已清空（该例外真的不再失败），
输出从"全部达标（另有 1 项已知例外）"变成**"✅ 全部达标"**。

> 教训：遇到"两个需求冲突"时，先检查是否**已有**别的令牌满足其中一个需求 ——
> 那比新建令牌更省事，也不会留下两套语义相近的蓝色。
> 原判断"数学上无解"只对"同一个令牌"成立，对"同一组令牌"并不成立。

### 六.11 设置与主界面：从"两个窗口"到"一个窗口两个视图"（第 22 轮）

**改动前**：设置是一个**独立的无边框 BrowserWindow**（`managerWindow`）——
980×720、居中浮动在聊天窗口之上、`frame:false` + `skipTaskbar`，
点主界面右上角「设置」弹出，关掉后回到聊天窗口。

**改动后**：设置变成**主窗口内的一个全尺寸原生视图**（`settingsView`），
与 ChatGPT 视图（`chatController.view`）**互斥显示**。

| | 视图 | 位置 | 尺寸 |
| --- | --- | --- | --- |
| ChatGPT | `chatController.view` | `y = 112` | `宽 × (高 − 112)` |
| 设置 | `settingsView` | **`y = 0`** | **`宽 × 高`（满高）** |

设置视图 `y=0` 且满高，正是"**设置和主界面一样大（含顶部工具栏）**"的实现 ——
它盖住的那 0..112px 恰好就是 ChatGPT 工具栏所在的区域。

**为什么必须用原生视图，不能靠 CSS 隐藏**：

> ChatGPT 页面是 `WebContentsView`（**原生层**），它盖在 renderer 的 DOM 之上。
> 给 DOM 元素设 `display:none` **盖不住一个原生视图**。
> 只有原生层之间的 `setVisible()` 才能互相遮挡。

**为什么不让两个页面共用一份 CSS**：

> `browser.css` 自带 `:root{--border/--text/--muted/--green/--red}`，
> 与 `design-tokens.css` **同名不同值**（前者是 ChatGPT 风格）。
> 若两套 CSS 同时加载，设置页的 `var(--border)` 会拿到 ChatGPT 的色值，**颜色全乱**。
> 分成两个视图后，两套 CSS 各自隔离。

**连带改动**（漏任一项都会出错）：

| 文件 | 改动 | 漏掉的后果 |
| --- | --- | --- |
| `electron/main.js` | 删 `openManagerWindow()`，新增 `createSettingsView` / `setActiveSurface` / `surfaceBounds` | — |
| `electron/main.js` | `WebContentsView` 加入 import | **`WebContentsView is not defined`，应用启动即崩** |
| `electron/main.js` | `manager:open/close` 改为切换视图 | — |
| `electron/main.js` | 新增 `chatWindow.on('resize')` 同步两个视图尺寸 | 拉伸窗口后设置视图留下空白边 |
| `renderer/index.html` | `×` 关闭按钮 → `← 返回主界面` | **进了设置出不来** |
| `renderer/styles.css` | 删 `.manager-window-bar` 的 `-webkit-app-region:drag` | 拖动顶部栏不移动任何东西（误导） |
| `renderer/styles.css` | `.boot-screen` inset `46px 8px 8px` → `42px 0 0` | 边缘露出一圈底色（浮动窗口的余留） |
| `renderer/design-tokens.css` | 删 `--danger-hover`（唯一消费者是那个 `×`） | 死令牌，看起来还在用 |
| `electron/preload.js` | `closeManager` → `closeSettings` | 名字说"关窗口"，实际是"返回界面" |
| `electron/browserPreload.js` | `openManager` → `openSettings` | 同上 |

**判据**：
1. 设置视图的 `bounds` 必须是 `y=0` 且 `height=内容区高度`（**满高**）。
2. 两个视图的可见性必须**互斥** —— 正在看的那个 `visible=true`，另一个 `false`。
   两者同时为 true 会在设置页下面露出 ChatGPT。
3. 进设置的入口与回主界面的出口必须**成对存在**（`openSettings` / `closeSettings`），
   且出口在界面上可见（左上角按钮）+ 键盘可达（Esc）。

**这一轮的教训（重要）**：

> 上一轮（第 21 轮）收缩 `pageMeta` 时把解构写成 `const [, title, subtitle]` ——
> 那是**三元组**时代的写法。用在二元组上会取到 `[说明, undefined]`，
> 9 个页面的 H1 全变成说明句。**而测试当时也是绿的**，因为断言恰好照抄了
> 同一处错误 —— **测试与代码犯了同一个错，于是双双通过**。
>
> 这个 bug 一直活到第 22 轮的运行时冒烟才被抓出来。

**教训**：① 测试必须表达**期望的事实**，不能照抄实现里写的东西；
② 只读源码的测试**证明不了运行时行为**，架构类改动必须配运行时验证。

### 反例补充（第 14 轮拆解覆盖层时发现的潜伏缺陷）

这三个缺陷都是原代码就存在的，只是被覆盖层的 `!important` 掩盖着，
拆解后才暴露。记录下来，因为它们代表同一类错误：**用覆盖掩盖问题**。

1. **`<html>` 在深色主题下背景一直是浅色**
   —— 浅色令牌块的选择器只写了 `body[data-theme="light"]`，
   不匹配 `<html>`；而 `theme-bootstrap.js` 会同时给 `<html>` 和 `<body>`
   设 `data-theme`。于是 `<html>` 一直落在 `:root` 的深色令牌上，
   表现为浅色背景——被 fixed 定位的 `.app-shell` 遮住才没暴露。
   **修法**：选择器改为 `:root[data-theme="light"], body[data-theme="light"]`。
2. **关闭按钮前景对比度不达标**
   —— `#555` on `#141414` 实测仅 **2.47:1**，低于 3:1 最低要求。
   改用 `var(--chrome-text)` 后达 **7.57:1**。
3. **`.log-panel` 的 `padding:0` 意图被静默覆盖**
   —— 内嵌层的 `.panel{padding:18px!important}` 压过了
   `.log-panel{padding:0}`，使日志面板本应贴边的工具栏/输出区
   被推入 18px 内边距。折叠去重后，基础意图自然恢复。

**共同教训**：`!important` 不只让"改样式"失效，它还会让**原本正确的局部意图
静默失效**——而且失效方式是"看起来还行"。这类缺陷不会报错，只会让界面
比设计者预期的更差一点。

### 七.1 运行时冒烟（第 22 轮新增，为什么必须有）

第 22 轮改动的是**窗口/视图架构**（原生层），踩到一个此前一直没人发现的坑：

> `tests/` 里 100+ 条测试**全部是"读源码文本做正则匹配"**。
> 它们能证明"代码里写了什么"，**证明不了"应用跑起来是不是这样"**。

第 21 轮留下的 `const [, title, subtitle] = pageMeta[page]` 就是活证据：
`pageMeta` 当时已收缩为二元组 `[标题, 说明]`，而 `[, a, b]` 是**三元组**写法
（逗号跳过下标 0）。结果 9 个页面的 H1 全变成说明句、副标题全空 ——
**而测试一直是绿的**，因为那条断言恰好也写成了 `[, title, subtitle]`，
**测试与代码犯了同一个错，于是双双通过**。

更隐蔽的是：这条 bug 在纯静态检查下几乎不可见，因为正则仍能匹配到那段文本。
只有**真的把应用跑起来、读 DOM 里的实际文字**才会暴露。

因此本轮的验证分三层，缺一不可：

| 层 | 手段 | 能证明什么 | 能否进 CI |
| --- | --- | --- | --- |
| 静态 | `tests/*.test.js` 正则匹配 | 代码写了什么 | ✅ 能 |
| 契约 | 棘轮 + 对比度 | 没有新增样式违规 | ✅ 能 |
| **运行时** | CDP 驱动真实应用 | **跑起来是不是这样** | ❌ 需 GUI |

运行时冒烟脚本在仓库外 `gpt-webcodex-ui-重构/_smoke-*.js`，共五组：

- `_smoke-cdp.js` —— 表面切换、API 命名、尺寸、无 JS 异常
- `_smoke-strict.js` —— **像素级**：设置页顶部像素必须等于它自报的底色，
  且 ≠ ChatGPT 工具栏颜色（证明原生视图真的盖住了工具栏那 112px）
- `_smoke-titles.js` —— 逐页读 `#pageTitle` / `#pageSubtitle` 实际文本
- `_smoke-cycle.js` —— 连续进出 6 次，确认设置视图**只创建一次**、无堆积
- `_smoke-resize-final.js` —— 对真实窗口 `setContentSize`，读
  `contentView.children` 的**原生 bounds** 验证两条不变式

**用法**（需先带调试端口启动）：

```bash
# 启动（9401=渲染层调试，9402=主进程调试）
./node_modules/electron/dist/electron.exe . --remote-debugging-port=9401 --inspect=9402
# 另开终端，依次运行
node gpt-webcodex-ui-重构/_smoke-cdp.js
node gpt-webcodex-ui-重构/_smoke-strict.js
node gpt-webcodex-ui-重构/_smoke-titles.js
node gpt-webcodex-ui-重构/_smoke-cycle.js
node gpt-webcodex-ui-重构/_smoke-resize-final.js
```

> **踩坑记录**：调试端口被占用时 Electron **不会报错退出**，而是静默启动一个
> "无调试端口"的实例。于是可能出现**两个实例同时在跑**，而脚本只连到其中旧的那个，
> 读出的数据自相矛盾（窗口尺寸显示 A、视图 bounds 显示 B）。
> 排查手段：`netstat -ano | grep :9401`，一个端口只能有一个 PID；
> 若有多个 electron.exe，先全部结束再启动。

### 七.2 "看着像是好的"是最危险的状态（第 23 轮：一个从未被人看见过的占位）

第 23 轮要做的事情本身很小：确认合并之后启动时不会"露出占位/白屏"。
但实测下来的结论和预想的完全不同。

**先说结论**：`browser.html` 里那个"正在打开 ChatGPT"的加载占位，
**从被写下的那天起就没有任何人看见过**。这不是修辞，是像素级的事实：

| 对象 | 几何（实测） |
| --- | --- |
| 宿主页 `.loading-stage`（占位） | x0 y112 1346×752 |
| ChatGPT 原生视图 | x0 y112 1346×752 |

两者**逐像素重合**。而原生 `WebContentsView` **永远合成在宿主页 renderer 之上**
（这正是第 22 轮合并方案的技术前提）。所以占位被永久遮挡 —— 它在 DOM 里
`display:grid; visibility:visible`，看着一切正常，但用户永远看不到。

**代价是多少**：用 `document.visibilityState` 与页面实际内容轮询测得

```
+0.86s  窗口进入可见状态（用户开始看到界面）
+0.90s  ChatGPT 视图 readyState=complete，但文字 0 字符、子元素 0
+3.58s  ChatGPT 首次画出真实内容
        → 用户盯着一块纯色空白（原生视图自己的 #f7f7f8）长达 2.72 秒
```

**修法**（`chatViewController.js` 的"可见性闸门"）：
首次内容就绪前**不显示**原生视图（`setVisible(false)`），视图一藏，
下面宿主页的占位就真的露出来了 —— 那正是它存在的意义。
就绪后再显示。实测空白期从"无解释的纯色"变成"有解释的转圈"。

**这次踩到的四个坑，每一个都值得记下来**：

1. **不能"事件一来就放行"**。`did-stop-loading` 在一个生命周期里会触发**两次**：
   第一次是初始空文档（+0.9s，0 字符），第二次才是真正的 ChatGPT。
   看到第一个事件就放行，用户看到的仍是空白 —— 闸门等于白设。
   最终改为**直接问页面**（`childElementCount` / `innerText`）而不是信事件顺序，
   理由是两次实测的事件时序并不相同，靠顺序判断不可靠。

2. **`executeJavaScript` 在加载期间会把 `did-stop-loading` 监听器撑爆**。
   看门狗每 150ms 问一次页面，一轮 2 秒的加载里挂了十来个临时监听器，
   触发了本仓库从未出现过的
   `MaxListenersExceededWarning: 11 did-stop-loading listeners added`。
   修法是给探询加 `isLoading()` 闸门 —— 加载中本来就不该问
   （那时必然没内容，问了也是白问，还留副作用）。
   **这个告警是我引入的**，用改动前后的启动日志对比确认，没有靠猜。

3. **测试脚本的判据必须和应用用同一个信号**。harness 早先只读 `innerText`，
   而布局未完成时它返回空串，于是出现"应用已按 `childElementCount` 正确放行、
   harness 却报没内容"的**假失败**，白白多花了两轮。测什么就要读什么。

4. **采样时机不对也会造出假失败**。最早那次几何采样发生在 CSS 应用之前
   （FOUC），读到 `y202 1330×91`（1330 = 1346−16，正是默认 `body{margin:8px}`
   吃掉的宽度），看着像"占位没铺满"。改为只在"窗口已可见且闸门正压着"
   那个窗口期记录几何 —— 那也正是用户真的在看占位的那几秒。

**方法论收获（比上面四个坑更重要）**：

- **"不可见"要分两种**：`display:none` 那种"明确关掉"，和本案例这种
  **"写着可见、实际被上层原生视图盖死"**。后者不会报错、不会让任何静态测试
  变红、截图（截 DOM 层）看着也完全正常 —— 属于最难发现的一类问题。
- **原生层与 DOM 层叠加时，判断"用户看到什么"必须看原生 bounds 与合成结果**，
  DOM 的 `getComputedStyle` 只能说明 DOM 自己的意图，说明不了最终画面。
- 因此本轮的验证脚本一律以**"真实 URL + `getVisible()` + 页面实际内容"**
  三个原生/运行时事实为准，不用任何猜测性的信号。

**新增脚本**（均在 `gpt-webcodex-ui-重构/`）：

- `_probe-placeholder.js` —— 占位可见性专项排查（DOM 几何 × 原生 bounds 对照）
- `_probe-startup-timeline.js` —— 启动时间线（窗口可见 → 内容就绪各耗时）
- `_verify-placeholder-fix.js` —— 闸门修复的 6 条判据验证（**已全绿 6/6**）
- `_shoot-placeholder-compare.js` —— 用 desktopCapturer 抓**整窗合成**截图
- `_diag-reveal.js` / `_diag-maxlisteners.js` / `_count-listeners.js` —— 排查用

**关于截图取证的一个要点**：证明这类问题**必须用 `desktopCapturer` 抓整窗合成画面**。
`Page.captureScreenshot` 只截宿主页 renderer，得到的是"占位画得好好的" ——
而那从来不是用户看到的画面。本问题的证据以**几何 + 时间线**为主（见上表），
截图只作辅助；"修复前"的空白画面没有截图存证（修复后无法在已修好的代码上
重现该状态），已删除一张试图模拟却被证实无效的对照图，避免留"看似证据实则不是"的材料。

**棘轮怎么收紧**：整改掉一批存量违规后，运行
`node scripts/check-css-ratchet.js --update` 把基线降到新值。
该命令**拒绝让基线变大**（只允许收紧），否则棘轮就失效了。

## 八、维护

- 本文档与 `design-tokens.css` 必须同步。改令牌值时必须更新本文的表格。
